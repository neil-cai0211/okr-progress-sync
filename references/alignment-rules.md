# OKR 对齐判断规则

## 三种对齐路径判定优先级

按精确度从高到低依次判断，命中即停：

### 路径 A：KR 级直接承接（精确匹配）

**判定条件**：Leader 的某条 KR 文本里直接 @ 了该组员。

**识别方法**：
1. 从 `+cycle-detail` 返回的 Leader KR 内容中，检查 ContentBlock 的 mention 列表。
2. mention 里的 open_id 与组员的 open_id 一致 → 命中。
3. 同时看 KR 文本末尾是否有 `@姓名` 的纯文本写法，作为辅助验证。

**回填位置**：直接对应这条 KR，不需要软判断。

**示例**：
- Leader KR1：「改进直播产品评分最低的三项功能，减少负反馈比例至10% @王颖颖」
- 组员：王颖颖
- 结论：王颖颖的进展 → 直接回填到 KR1

---

### 路径 B：O 级对齐（软判断匹配）

**判定条件**：组员的 O 通过飞书 OKR 的「添加对齐」功能，对齐到了 Leader 的某个 O。

**识别方法**：
```bash
# 查组员 O 的对齐关系（aligning = 我对齐了谁）
lark-cli okr objective.alignments list \
  --objective-id "组员O_ID" \
  --align-type "aligning" --page-all --as user
```
- 返回的 `to_entity_id` 就是被对齐的目标 ID。
- 如果 `to_entity_id` 等于 Leader 的某个 O 的 ID → 命中路径 B。

**软判断流程**：
组员对齐了 Leader 的某个 O，但一个 O 下有多条 KR。需要判断组员的每条进展对应 Leader 的哪条 KR。

判断步骤：
1. 列出 Leader 该 O 下的所有 KR 文本。
2. 读组员的每条 KR 文本和最新进展内容。
3. 语义对比：组员 KR 的主题和 Leader 哪条 KR 的主题最接近？
4. 置信度分级：
   - **高（直接写）**：组员 KR 文本和 Leader KR 文本高度重合，或关键词直接对应。
   - **中（问用户）**：大致方向相关，但具体对应哪条 KR 不唯一。
   - **低（问用户）**：组员进展内容很泛，看不出对应 Leader 哪条 KR。

**软判断举例**：
| Leader KR | 组员 KR | 判断 |
|---|---|---|
| KR1: 改进直播产品评分最低的三项功能 | 组员 KR1: 完成道具商城负反馈分析 | 高 → 对应 KR1 |
| KR2: 客户留存率提升至60% | 组员 KR2: 优化新用户引导流程 | 中 → 问用户 |
| KR3: 直播小窗卡顿率下降至1% | 组员 KR3: 完成用户调研问卷 | 低 → 问用户 |

**多对多情况**：组员一条进展可能同时支撑 Leader 的多条 KR。这时把同一段内容拆分或复制，分别回填到对应的 KR 下。

---

### 路径 C：无对齐关系（跳过）

**判定条件**：
- Leader 的 KR 里没有 @ 这位组员。
- 组员的 O 也没有对齐到 Leader 的任何 O。

**处理方式**：跳过，不做任何写入操作。在最终汇总报告里列出「已跳过：XX（无对齐关系）」。

---

## 常见边界情况

### 1. 组员对齐了别人，不是对齐当前 Leader
- 说明这位组员的汇报线不在当前 Leader 这里。
- 跳过，不写入当前 Leader 的周报。

### 2. 一个组员对齐了 Leader 的多个 O
- 正常情况，说明这个组员横跨多个目标。
- 分别判断每条进展对应哪个 O 下的哪条 KR，分别写入。

### 3. Leader 的 KR 里 @ 了多个人
- 每条 KR 下可能有多个组员承接。
- 每个组员各自的进展分别创建一条新记录，互不干扰。

### 4. 组员自己写了多条进展记录
- 默认取最新一条。
- 如果用户要求合并历史几条，再按用户指示处理。
